# melchordgen

**A VST3 that listens to the loop on its track and plays a fitting MIDI part back.**

Drop it on an audio track as an effect, press Listen, and it captures the next N bars from the downbeat, works out the key and the chord per bar, and generates a complementary MIDI line, in key and locked to the host transport. Route the MIDI to any instrument, or drag a `.mid` straight out of the plugin.

**MVP in one sentence:** listen to a loop, detect its key and chords (with a two-click manual override), generate in-key, groove-locked complementary MIDI, and make it recordable in the DAW.

Built in C++17 on JUCE 8.0.14. Windows VST3, tested in Ableton Live 12. Status: **in progress**, working end to end, not yet at the quality bar it is being built to.

> This is a public showcase. The plugin source, the training data, and the model weights are private. What is here: the product, the module map, the Python training and data pipeline at a high level, and the blind listening-study method that decides what ships.

## What works today

- **Loop capture.** Press Listen while the transport rolls; the capture arms, waits for the next bar boundary (host PPQ), and records N bars (4 by default, up to 8) of mono audio into a pre-allocated buffer. The audio-thread entry point does no allocation and takes no locks: it copies samples and flips atomics.
- **Key and chord detection**, built in-house and license-clean (no copyleft analysis libraries). A peak-based HPCP chroma (4096-point STFT, 2048 hop, Hann window, spectral peaks only, parabolic frequency refinement, folded to 12 pitch classes over MIDI 36-96) so the broadband energy of drums drops out and the harmony survives. Key by Krumhansl-Schmuckler profile correlation over all 24 major and minor keys; chords per beat segment by cosine-similarity template matching over 12 roots x 5 qualities (maj, min, 7, maj7, m7). Both return a confidence (winner minus runner-up), and the UI exposes a one-click key override that the generator reads instead of the raw detection.
- **Transport-locked MIDI generation.** A deterministic rule-based generator turns the analysed context into a line: mid register, moderate density, motif plus call-and-response, chord tones on strong beats, sparser when the loop is busy and busier when it is sparse, rhythm derived from the loop's own 16th-note groove profile. A scheduler emits exactly the note on/off events that fall inside each processing block, with sample offsets derived from the event's PPQ position relative to the block start (never from the last event time, the classic out-of-range bug) and clamped to the block. It loops, survives BPM changes and scrubbing, and the audio thread reads only a swapped, pre-built line.
- **Drag-out `.mid`.** A drag zone in the UI writes a Standard MIDI File (format 0, TPQN 96, tick-unit timestamps, matched note pairs) of the current line and hands it to the host or the file system. The file the test suite round-trips is the same file the drag produces.
- **An optional ML engine behind the same interface.** The plugin can spawn a warm Python sidecar that holds a fine-tuned music transformer on the GPU and answer `listen` / `generate` requests over a localhost JSON-lines socket from a background thread, with a hard read deadline so a stuck sidecar can never hang the plugin. On any failure the plugin falls back to the rule-based line. Measured on an RTX 3080: 5.3 s warm load once per session, 0.8 ms ping, generate-ahead round trip median 329 ms (max 1385 ms on the first bar) against a 1778 ms per-bar budget at 135 BPM, about 5.4x headroom.
- **A constraint layer** ported one-to-one from the Python QA screens, with parity vectors generated by the reference implementation: melody-chord clash count (must be zero in every style), big-leap and note-count floors per style profile, distinct-pitch-class floor, a "static" warning, a tense-hold warning for a b9 held over its own bass for 1.5 bars or more, and a transposition-invariant chord-sequence avoid list.

### Honest limits

- Notes only, no CC. 4/4 assumed. Tempo comes from the host.
- The in-plugin key detector was wrong on roughly one loop in three on dense material in its first version; the later dual-method detector went 3 of 3 and 10 of 10 on small held-out sets, which is evidence of improvement, not a measured accuracy. The override exists because detection will sometimes be wrong.
- The rule-based line is competent and controllable, not yet the "amazing" the project is aiming at. That gap is what the ML pipeline and the rating study below are for.

## The training and data pipeline (Python)

The premise of the ML side is personalization: the engine is being trained on one producer's own catalog and steered by that producer's own ratings. The claim under test is "this engine can learn one specific person's taste", never "this generalizes".

**Engine.** A 360M-parameter pretrained music transformer (anticipatory music transformer family, arrival-time token vocabulary) wearing small LoRA adapters, each with one job (chords, melody cohesion, colour from liked-track harmony), stacked at inference. The adapters are trained locally on an RTX 3080 or on a rented GPU pod, with a held-out validation file (per-sequence splits leaked near-duplicate sections across sides and made the validation curve lie), early stopping on the validation minimum, and TensorBoard telemetry.

**Harvesting MIDI from Ableton projects.** The corpus is 2,094 Ableton Live project files plus 459 liked tracks (the likes are used only for steering features, never as training data, and never reproduced). A parser reads the gzipped `.als` XML directly: every `MidiTrack`, every `MidiClip`, every `KeyTrack` / `MidiNoteEvent`, with arrangement start and end so overlapping clips can be grouped into **sections** of layers that actually played together. A second pass reads each track's MIDI Pitch device and applies its transpose, because the projects are written in C and pitched at the device, and the sounding key is what matters for both training and detection. A full-drive sweep for loose `.mid` files was also run and deduplicated by content hash (33,087 paths, 26,671 unique, 19,922 new after hashing against the existing set, 362 with key/BPM labels in the filename); most of it was third-party packs and was tagged as prototype-only.

**Dataset building.** Per-source provenance tags decide what a shippable model may be trained on (public-domain Bach chorales as a voice-leading base: about 370 chorales into 1461 accompaniment pairs of "given these voices, generate the missing one"; the producer's own sections as the taste layer; third-party packs prototype-only). Weighted and augmented datasets are assembled from these tiers, and a movement-profile pass over 5,932 harvested sections measured the melodic onset-count and interval bands per harmonic-rhythm context that the generator now targets.

**Provenance law.** Nothing joins the live engine unless its cook (training command, inputs, and hashes) is committed before its blind A/B. Trainers write a `provenance.json` birth certificate into every adapter; an adapter without one is treated as unreproducible. A manifest lists every live component with its status (recookable from disk, code in repo, or an explicitly flagged fossil), and the census re-runs at every era close.

**Back-testing generations.** Every generated clip passes a gauntlet before a human hears it: a pre-check script with nine mechanical checks (source hash seal, an 8-bar cut at the named BPM within 1%, audibility, the clip screens, MIDI tempo stamp within 0.2 BPM of the sample's fine tempo, chord-change phase within 40% of a bar of the downbeat, a preregistration block with both outcome branches written down, key and BPM metadata consistency), then the screens above. Candidate metrics are treated as hypotheses and back-tested against historical ratings before they can influence anything. One embedding-based "does this sound like him" scorer was adopted in the morning and killed the same day when its within-batch pairwise agreement with past ratings came out 0 of 6 (chance is 50%); it survives only for style-level tagging, never for ranking takes.

## The blind listening study

Every clip gets a score from 1 to 5. "Fire" means 4 or better. Defaults are adopted only when a candidate beats the incumbent in a blind A/B on the same day at the same standard, and several ties were resolved in favour of the cleaner lineage rather than the newer one.

The milestone question: **how long until any sample produces fire at least 2 times in 3?** The measurement is a sealed pool of fresh samples never tuned against, each used exactly once and burned after exposure, three regenerations per exposure, pass at 4+ on 2 of 3. Pass rate and ground-class coverage are tracked as separate units, the rate is not interpretable until 10 or more fair tests, and every rate is printed with an exact 95% confidence interval. A single 3-of-3 pass carries the interval [0.29, 1.0] and a 2-of-3 pass [0.09, 0.99], which is why no single pass licenses a claim.

Where it stands: the first measurement era closed at **8 of 17** samples passing (exact 95% interval [0.230, 0.722], point estimate 0.47; takes per sample are not fully independent, so the true interval is wider). The two-in-three target was not met. A second era on a harder pool closed its threshold at 1 of 12, with the interval at ten tests reading [0.003, 0.445]; the two intervals overlap, so the eras are not statistically separable at this depth. Every miss carries a diagnosed mechanism, and several of them became generator rules.

The rater's own reliability was measured too. A blind re-serve of a burned batch reproduced the original ratings exactly at n=3; a second, truly blind re-serve a week later came back exactly one point lower on every clip, pooled agreement 0.571 at n=6 against a 0.70 kill line committed before any serve ran. The pre-committed decomposition ruled it drift, not noise (uniform deltas, rank order preserved, the same specific complaint reproduced blind seven days apart): the bar rises about a point per week on old material, by design, and every counted milestone test was rated same-day so the scorecard is drift-immune.

The full method, its limits (N=1, no randomized exposure ordering, no washout accounting), and the three self-disproof attempts that the project's confidence actually rests on: [docs/EVALUATION-METHOD.md](docs/EVALUATION-METHOD.md).

## Build and test

Requirements: CMake 3.22+, a C++17 compiler. JUCE 8.0.14 is fetched by CMake on first configure.

```powershell
pwsh tools\gate.ps1        # configure + Release build + ctest; prints GATE: GREEN or GATE: RED
```

The gate is run before every commit and is never weakened to pass. The VST3 lands at `build\melchordgen_artefacts\Release\VST3\melchordgen.vst3`; copy it to `%CommonProgramFiles%\VST3\` and rescan.

Eleven ctest targets cover the host-independent core, every one of them JUCE-free except the MIDI-file round trip: `triad_schedule`, `loop_capture`, `key_detect`, `chord_detect`, `character`, `musical_context`, `generator`, `initiation`, `sequence_avoid`, `screens`, `midi_export`. Two local-only tools grade key detection against a folder of reference loops with known keys and render the generator's output to `.mid` for a rating batch.

### Using it in Ableton Live

1. Put your loop on an audio track and add melchordgen as an audio effect. Audio passes through untouched.
2. Open the UI, pick the bar count, press **Listen** while the beat plays. It captures from the next downbeat, analyses, and shows the key and the chords. If the key looks wrong, fix it in the dropdown; the line regenerates.
3. Hear it: on a MIDI track with a synth, set **MIDI From** to the audio track, choose **melchordgen** (the post-FX tap), set **Monitor** to In, arm, and press play.
4. Keep it: drag from the **drag MIDI out** zone onto a MIDI track or a folder.

## What is next

1. Close the gap between the rule-based line and the fine-tuned engine inside the plugin (the sidecar path exists; an in-process CPU/quantized port is the distribution lift).
2. Continuous listening (re-analyse as the loop changes) and a chord-following mode for progressions that move.
3. Then, and only then, UI polish. The kill list until the core is great: generating audio, ML for its own sake, and audio tempo detection (the DAW hands tempo over for free).
